Agentic SDLC · Runtime Trace

End-to-End Execution View

Purpose. One unit of work traced through the whole machine — source → trigger → spawn → code → sandbox test → gates → PR → optional human review → production → monitor → teardown — naming the real technology and integration at each hop. This is the motion view (the logical diagram shows structure; the physical diagram shows deployment).

Step by step

0

Source — where a unit of work is born JIRA

A ratified, ACTIVE spec in JIRA (produced by the PM → Spec chain), decomposed into a build-ready unit-spec with Gherkin acceptance criteria.

Alternate sources: a Drift Reconciler finding (code ≠ spec), or a Monitor incident — both enter the same pipeline.

JIRASpec-as-code
1

Trigger — what starts a run Zone 2

A human (or the system) moves the JIRA issue to “Ready for Agent.” A JIRA webhook hits the JIRA⇄Azure DevOps bridge ingress. The Orchestrator admits the run — checks a ratified spec exists and blast-radius is within policy (OPA/Rego) — writes run-start to the audit ledger, and enqueues a job on Azure Service Bus.

JIRA webhookOrchestratorService BusOPA policy
2

Spawn the worker — container, not VM Zone 3

The Orchestrator requests a fresh, ephemeral sandbox per run: an Azure Container Instance (or Container Apps Job), spawned on demand and torn down after. Containers, not VMs — faster spawn, cheaper, sufficient isolation when properly sandboxed. The worker gets a short-lived, least-privilege managed identity (secrets from the agentic plane’s own Key Vault) and can reach only the Model Gateway, the dedicated agentic cluster, and the repo seam — never the application data cluster.

Azure Container InstancesManaged IdentityKey Vault (own)
3

Check out the code — the repo seam seam

The worker runs git checkout of the target branch from Azure DevOps Repos into the sandbox — a clean, isolated working copy. This live checkout is why the Coder can’t hallucinate current code: it reads reality, not memory. Code flows in across a seam; nothing is shared.

Azure DevOps Repos
4

Coder — generate the change Zone 3

The worker loads context: the ACTIVE spec (Gherkin criteria), the KB via structure-scoped retrieval (Serena graph + Atlas Vector), and episodic memory (check-before-act lessons). OpenHands / Cline drives the edit loop, writing code + tests. Every model call routes through the Model Gateway — redaction, token budget, audit. Only code + spec ever leave the tenant; no regulated data, ever.

OpenHands / ClineSerenaAtlas VectorModel GatewayClaude / GPT
5

Sandbox testing — where verification runs Zone 3

In the same ephemeral sandbox, the worker executes the generated acceptance tests (from Gherkin), the existing regression suite, type-checks and linters, and — for integration work — Pact contract tests at the seams plus oasdiff on the API surface. Any datastore needed is an ephemeral test DB / fixtures, never production data. This is “verify by execution, not opinion” — running code is the truth signal.

Test runnersPactoasdiff
6

Gates — the validation gauntlet Zone 3

Spec-conformance (do acceptance tests pass?), blast-radius + OPA/Rego policy (auth/payments/PII → stricter path), an adversarial Verifier/Critic (independent agent tries to refute), a breaking-change check (oasdiff), and regression green. Every result lands in the audit ledger. A failed gate triggers a bounded retry (back to the Coder) or an escalation to a human.

Spec-conformanceBlast-radiusOPA/RegoAdversarial Verifier
7

Commit — how code moves toward prod seam

The worker pushes a branch and opens a Pull Request in Azure DevOps Repos, linked to the JIRA issue, carrying the full evidence pack (spec link, gate results, diff, blast-radius, eval evidence). Azure Pipelines CI runs on the PR — the authoritative re-verification on neutral infra, independent of the sandbox. Belt and suspenders.

Azure DevOps Repos (PR)Azure Pipelines

8 · Optional human review & approval

Driven by the autonomy ladder and the risk/confidence of the change:

ConditionPath
L3 · low-risk module · all gates + CI green · high confidence Auto-merge  No human in the path.
L2 · or high-risk (auth/payments/PII) · or low confidence · or a gate flagged Human approves  Reviewer inspects diff + evidence pack in ADO / JIRA, then approves or requests changes.

Optional by design: the gates & evals make review safe to skip for proven low-risk classes, so the human is the exception path, not the default bottleneck. Even on auto-merge, a human is on the loop — notified, with a kill switch.

9

Deploy to production — dark, canaried, reversible Zone 1

On approval/auto-approve, the PR merges to main; Azure Pipelines builds the artifact and deploys to the App Service staging slot first. It ships dark — live but with the homegrown feature flag OFF. A canary ramps (slot-swap / gradual flag %) watched by the Deployer + Monitor. On any error/regression breach, auto-rollback / kill-switch reverts instantly (flag-off or slot-swap-back).

App Service slotsFeature flags (homegrown)Canary + rollback
10

Close the loops & tear down Zone 1 → 2

Monitor confirms health (via the read-only telemetry seam) → ramps the flag to 100% or holds. Then: KB re-sync (Serena + Atlas re-index = definition of done), Drift Reconciler re-checks spec↔code coherence, episodic memory records the outcome as a lesson, the audit ledger seals the run trace, and the PM↔outcome loop asks whether the success metric moved. The ephemeral worker is destroyed — zero persistent state.

The three invariants this trace never violates

IsolationThe worker touches the app only through seams — repo checkout in, deploy service-connection out, read-only telemetry in. No shared datastore, ever.
No regulated data to modelsOnly code + spec cross the Model Gateway. Customer / financial data never enters a model context.
Every hop is auditedTrigger, spawn, model call, gate, merge, deploy, rollback — all land in the immutable ledger.
