# Dep Diff — Correlate Version Changes with Gotcha Cards

**Date:** 2026-07-25
**Status:** Draft for review (rev 2 — early exit, queue ownership,
trust-graded queueing, advisory cadence)

## Problem

`drift.py` detects when manifests change (`requirements.txt`, `package.json`,
etc.) and flags them generically: *"Re-run deps0 and re-verify
09-dependency-practices cards."* This tells the founder *something changed*
but not *what* changed or *which cards* are affected.

`deps0.py` already captures exact pinned versions at pin time and tags
risk-sensitive packages (stripe, razorpay, crypto, etc.). The gap is that
`drift.py` runs the diff but `deps0` knows the versions — they are never
connected.

## Solution

New script: `dep-diff.py`. Called by the post-commit ship loop alongside
`drift.py`. When manifests changed since the pin, re-runs the deps0
*parsers* at HEAD, diffs the version table against the pinned one, and
scans `09-dependency-practices.md` for cards mentioning the changed
packages.

## Design

### Early exit (per-commit cost)

Before parsing anything:

```
git diff --name-only pin..HEAD -- . ':(exclude).speccraft'
  ∩ {requirements.txt, pyproject.toml, poetry.lock,
     package.json, package-lock.json, pnpm-lock.yaml}
```

No manifest changed → exit 0 silently. This is the common case; per-commit
cost is one git diff. (drift.py already computes this set as `dep_changed`,
drift.py:163-166 — the ship loop may pass it in to skip even the git call.)

### Detection

```
1. Read pinned version table from kb/derived/dependencies.md (the old deps0
   output). Format is exactly what deps0 writes:  - `name` @ **version** ⚠risk
   — parse name, version, and carry the risk flag through.
2. Run the deps0 parsers at HEAD to get the new version table (same find()
   walk over manifests, monorepo-aware)
3. Diff: for each package present in both, compare versions
   - New packages (in HEAD, not in pin): report as new
   - Removed packages (in pin, not in HEAD): report as removed
   - Changed versions: report old → new
4. For each changed/added/removed package, scan
   kb/inferred/09-dependency-practices.md for cards mentioning it
5. If a match is found, report the card location
```

### Card matching

Substring grep on package names false-positives on short names ("click"
matches "click the button" in card prose). Match order:

1. Backticked mentions: `` `<name>` `` (how cards cite packages)
2. Fallback: case-insensitive word-boundary match (`\b<name>\b`) against
   heading lines only

Over-flagging is tolerable (this is review targeting, not a verdict), but
prose-level substring matching produces enough dumb hits to make the
founder stop reading the section.

### Output format

```
=== DEPENDENCY DIFF (pin abc1234 → HEAD def5678) ===

CHANGED VERSIONS (3):
  stripe  5.0.0 → 6.0.0  ⚠risk
    → 09-dependency-practices.md mentions `stripe`:
      - "Stripe v3 migration" (line 42)
      - "Stripe idempotency keys" (line 87)
  redis   4.2.1 → 5.0.0  ⚠risk
    → 09-dependency-practices.md mentions `redis`:
      - "Redis sentinel config" (line 134)
  click   8.1.0 → 8.2.0
    (no gotcha cards reference click)

NEW PACKAGES (1):
  anthropic  0.30.0
    → no existing gotcha cards — consider adding to 09-dependency-practices.md

REMOVED PACKAGES (0):

Suggestion: run deps0.py --config .speccraft/kbforge.yaml to re-pin deps,
then update or add gotcha cards for any changed packages in
09-dependency-practices.md.
```

### Queueing — trust-graded (--queue flag)

Queue items only for findings that are founder *work*, not context:

- **Card-matched changes** — a changed/removed package with matching gotcha
  cards: the cards may now be wrong. One item per package, listing the
  affected card lines.
- **Risk-tagged changes** — a new or changed package matching the RISK
  regex (imported from deps0), card or no card: risk-sensitive surface
  with no gotcha coverage is itself a finding.

Everything else (e.g. `click 8.1.0 → 8.2.0`, no cards, no risk tag) stays
in the report only. Queueing routine bumps would feed the founder-bottleneck
queue (critique #1) with non-work.

### Queue ownership (dedup vs drift.py)

`drift.py --queue` currently appends generic dependency-drift items
("`requirements.txt` changed — re-run deps0, re-verify cards"). Once
dep-diff is in the ship loop, **dep-diff owns dependency queue items** — it
has the precise story (which package, old → new, which cards). drift.py
keeps its console DEPENDENCY section but drops its dep-drift queue append.
Without this, every version bump produces two queue entries for the same
event, one vague and one precise.

### Integration with ship loop

`dep-diff.py` is called in `post-commit` alongside `drift.py`, before
`seed0` re-pins. The output is printed to the ship-loop log and appended to
`QUEUE.md` via `--queue` flag (per the tiering above).

### Implementation

`dep-diff.py` imports from `deps0.py` (same directory) — verified safe:
deps0 has a proper `if __name__ == "__main__"` guard (deps0.py:227) and its
module level is imports + the RISK regex + function definitions only.

Imports: `parse_pyproject`, `parse_requirements`, `parse_poetry_lock`,
`parse_package_json`, `parse_package_lock`, `find`, `RISK`.

**Never calls `audit()`.** The advisory scanners (pip-audit / npm audit) are
networked and slow; they have no place in the per-commit path. dep-diff is
parsers-only by contract.

### Advisory refresh cadence (the channel this spec must not let rot)

Excluding scanners from the per-commit path is correct — but it means CVE
data only refreshes when `deps0.py` fully re-runs, which today is manual.
New advisories against *unchanged* pinned versions are exactly the
external-world-changes-with-no-repo-change channel from critique #4, and
the advisory feed is the only such channel this system has.

Add a scheduled advisory refresh: a weekly cron / CI job runs deps0 (or a
`deps0.py --advisories-only` mode that skips the inventory rewrite), diffs
the new advisory JSON against `kb/derived/advisories-*.json`, and queues an
item only when new advisories appear against currently-pinned versions.
Deterministic (pip-audit at pinned versions), no LLM, in-discipline.
Without this, dep-diff sharpens the version-bump story while the advisory
story quietly rots.

### Relationship to `drift.py`

`drift.py` reports *that* manifests changed. `dep-diff.py` answers the
follow-up: *what exactly changed in the deps, and what KB knowledge does
that affect?* The ship loop calls both; dep-diff exits silently when no
manifest moved, and owns the queue entries when one did.

## Out of scope

- External API changes without version bumps (Stripe deprecates v3
  server-side with no package version change) — cannot be detected from
  inside the repo. The advisory cadence above covers the CVE channel;
  behavioral/contract drift of remote services remains open (changelog
  watching / contract tests are a different project). After this spec,
  critique #4 is partially resolved: repo-visible channel covered, remote
  behavior channel documented as open.
- Automatically updating gotcha cards — detection only, same discipline as
  the rest of the system.
